Coding and writing standards · Version 1 · September 2026

Tack Labs Standards

SOLID, KISS, DRY and YAGNI point at real problems. They are also too vague to review against. Two good engineers can read the same principle and reach opposite answers. This standard keeps the aim of each one and turns it into a rule you can check.

Gates block the merge

Formatters, linters, type checkers and tests run in CI. If a tool can check a rule, the tool checks it. Nobody debates those rules in review.

Foundations are defaults

F1 to F10 below. You may break one if you have a reason. Write the reason in a one-line comment. Reviewers then discuss the reason.

Writing is plain English

W1 to W6 cover docs, code comments and commit messages. They apply to every draft, whether a person or an AI wrote it.

The ten foundations

Each entry names the acronym it replaces and why that acronym is hard to apply. Then it gives the rule we use. In review, cite a rule by its ID, for example "see F3".

−DRYDon't repeat yourself
+F1Merge only what changes together

Merge only what changes together

DRY never says what counts as duplication. Merging two similar functions can produce code worse than either copy. Code that looks the same today often drifts apart within a year. Every merge ties the callers together, and sometimes that tie is wrong.

  • Two copies are fine. Extract a shared function when a third copy appears. Only do it if every copy changes for the same reason.
  • A shared helper that needs a boolean flag or a mode argument is really two functions. Split it back.
  • Business rules, limits, schemas and URLs live in one place. This part of DRY still holds.
  • Tests may repeat themselves. Each test should read top to bottom without jumping into helpers. Share builders for test data. Keep the assertions in the test.

CheckWould a bug fix in one copy always be needed in the others? If yes, merge them. If you are unsure, leave them apart.

−KISSKeep it simple, stupid
+F2Simple is measured

Simple is measured

Nobody defines "simple". Show two developers the same two functions and they may pick different ones. People who over-build usually believe the problem needed it.

Here, simple means code that meets these numbers. Linters enforce them where the language has a rule for it.

  • Cyclomatic complexity of 10 or less per function.
  • Nesting of 3 levels or less. Return early instead of wrapping code in another block.
  • A function fits on one screen, around 40 lines.
  • 4 parameters or fewer. Past that, pass one named options object.
  • A list of values is data. Store it as data instead of a chain of if statements.
  • A one-liner that needs a comment to decode gets rewritten as two plain lines.

The first version below repeats itself for each name. The names are data, so the fix is a set lookup.

−YAGNIYou aren't going to need it
+F3Remove your code

Remove your code

Nobody argues for unused code. It stays anyway. People keep it in case it is needed, or because it took hours to write. The useful rule is to delete it. Some flexibility is worth building early, and F10 covers that cheap kind: a small interface where code meets the database or network.

  • No commented-out code. Git keeps the history.
  • No unused parameters, flags, config keys, exports, variables or outputs.
  • No abstraction built for later. An interface with one implementation is allowed at an IO boundary, as in F10. It is also allowed when tests need a fake.
  • Every feature flag has an owner and a removal date. Put both next to the code that reads the flag.
  • A pull request that only deletes code is normal. Review it like any other.

CheckDead-code tools run in CI for each language. See the gates table.

−TDATell, don't ask
+F4Behaviour lives with the data it guards

Behaviour lives with the data it guards

Tell, Don't Ask is object-oriented design under another name. In the first example below, every caller must remember to raise the event after changing the name. Sooner or later one caller forgets.

  • Sometimes changing a field must also do something else. It might raise an event, record a time or validate the value. The owning type does all of it in one method. Callers cannot set the field directly.
  • Validate in the constructor. If an object exists, it is valid.
  • Values that should not change are immutable. Use records, frozen dataclasses or final fields with copyWith.
  • Request and response DTOs at the edges may be plain data. They are converted to domain objects at the boundary.

F5CQS kept. Change state or answer a question

Change state or answer a question

Command-query separation is worth keeping. A function either does something or returns something, never both. Standard libraries break this on purpose in a few places, for convenience.

  • The name says which kind a function is. get, find, is, has and count answer. save, send, create, apply and set change.
  • Four exceptions are allowed: try-parse, pop, get-or-add and moving an iterator forward. Use the language's own version. Do not invent new ones.
  • Render and build functions are queries. They never fetch, navigate or write state.
  • Property getters have no side effects.

CheckA function with a query name that writes anything blocks the merge.

−SRPSingle responsibility principle
+F6Group by feature, then by layer

Group by feature, then by layer

Nobody agrees what a "responsibility" is. Take one method that reads users and one that reads orders. Do they share a class because both read data? Or do they split because the entities differ? Push SRP too far and the code breaks into pieces too small to follow.

We split by entity, inside the feature that owns it.

  • Top-level folders are features, such as orders, invites and care_teams. Inside each are layers. The route or view calls the service or view model, which calls the repository.
  • A function does one operation, as in F5. A class holds what one feature needs from one layer. So UserRepository and OrderRepository each sit in their own feature.
  • Shared code such as the HTTP client, logging and auth lives in core or shared. Features depend on it. It never depends on a feature. Features never import each other's internals.
  • Split a class when its callers use separate halves of it. Also split when edits to one half keep breaking tests of the other. Do not split earlier.
  • Merging is as valid as splitting. Three classes that always change together are one class.

CheckCan you delete the feature by deleting its folder and its registration lines?

−OCPOpen for extension, closed for modification
+F7Reach for a named pattern when the second variant arrives

Reach for a named pattern when the second variant arrives

The open-closed principle says what to aim for and gives no method. Design patterns give the method. Strategy adds algorithms. Decorator adds behaviour. Visitor adds operations. Used too early, any of them is over-engineering.

  • Write the first variant directly. Add no extension point.
  • When a second variant arrives, pick a named pattern. Strategy swaps an algorithm. Decorator wraps extra behaviour such as retry, caching or logging. Adapter fits a third-party API to our interface.
  • Some languages have closed unions. A closed union lists every case in one type, and the compiler checks that each switch handles them all. Where you have one, prefer it to Visitor or a class per case.
  • Put the pattern in the type name, for example RetryingHttpClient or FlatRatePricing.

CheckEvery abstraction has at least two real uses today, or sits at an IO boundary.

−LSPLiskov substitution principle
+F8An override never refuses

An override never refuses

Liskov substitution comes down to using inheritance properly. In the example, Train inherits Turn() and throws. Code that accepts any vehicle now crashes when it is given a train.

  • An override that throws "not supported" is a design error. Fix the hierarchy, or split the interface as in F9.
  • Inherit only when the subtype can stand in for its parent everywhere. To reuse code, compose.
  • Classes are sealed or final by default. Opening one for inheritance is a deliberate choice.
  • One level of your own below a framework base class is normal. Three levels is a warning sign.

−ISPInterface segregation principle
+F9The caller owns the interface

The caller owns the interface

Interface segregation mostly repeats F6 and F8. A typical example is an IAnimal interface that makes every animal implement Fly() and Swim(). A cat then has to fake flying.

  • Declare an interface next to the code that calls it. List only what that caller uses.
  • Name it for what it can do, such as OrderStore, Clock or Notifier. Avoid an IOrderService that copies one class member for member.
  • One implementation, one caller and no IO means no interface. Use the class.
  • TypeScript types and Python Protocol match on shape. The implementation does not even need to declare the interface.

CheckEvery member of the interface has a caller in the module that declares it.

F10DIP kept. Invert dependencies at the IO boundary

Invert dependencies at the IO boundary

Dependency inversion earns its place. It shapes the architecture, reduces coupling between modules and breaks import cycles. It is also badly explained. Few people can say what "high-level" and "low-level" mean, so we define them here.

There are two kinds of dependency. A code dependency is one module importing another. Execution flow is one module calling another at runtime. Usually both point the same way. Inversion turns the import around. Calls still go the same way.

Low-level code touches the outside world. That means the database, network, file system, clock, random numbers, environment variables and platform channels. High-level code holds the business rules. The rules declare an interface. The IO code implements it.

  • Business rules never import a database driver, SDK or HTTP client.
  • The clock and randomness count as IO. Inject them so tests give the same result every run.
  • Each app wires its concrete classes in one place, called the composition root. That is usually main, the DI setup, the provider graph or the Terraform root module.
  • Modules may not import each other in a cycle. Break a cycle by inverting one import.

CheckSearch the domain folders for driver and SDK imports. There should be none.

Plain English, not Claudish

Claudish is the style AI assistants tend to write in. It is dense, padded and heavy with jargon. It sounds confident and says less than it seems to. People write it too, especially when rushed.

These rules cover everything we write in English. That includes docs, READMEs, runbooks, PR descriptions, review comments, code comments and commit messages. They apply whoever drafted the text. The person who commits it is the author.

W1
Lead with the point. The first sentence tells the reader what they need. Skip the greeting, the preamble and the closing summary.
W2
Short sentences, everyday words. Aim for about 15 words a sentence. Split anything over 25. Use the word swaps below.
W3
Every sentence carries a fact. Cut hedges, intensifiers and filler. If deleting a sentence loses nothing, delete it.
W4
Keep the facts exact. Names, numbers, paths, commands and identifiers stay exactly as they are. Keep precise technical terms. Explain each one the first time it appears.
W5
Plain punctuation and layout. Use full stops. Avoid dashes between clauses, asides in brackets and chains of semicolons. Bold only a warning. No emoji. Add headings only when a document is long enough to need them.
W6
Describe the code as it is. Docs and comments describe the current code. History belongs in commits. Nobody narrates with "I've updated", "we now" or "this ensures".

Documentation

This covers READMEs, runbooks, design notes, PR descriptions and anything else in docs/.

  • Start with what the reader will do or learn. Setup steps come before background.
  • One idea per paragraph, three or four sentences at most.
  • Number the steps. Put comparisons in a table.
  • Spell out each abbreviation the first time it appears.
  • Describe the system as it is. History goes in the changelog.
  • Copy commands, paths and code exactly, in code formatting.
  • Delete sections nobody reads. Short docs get read.
  • A PR description answers four questions. What changed? Why? How did you test it? What could break?

Code comments

  • Comment why, and only when the code cannot show it. Good names and structure already show what.
  • A comment describes the code as it is now. Never write "now uses", "updated to", "new approach" or "as discussed". That belongs in the commit.
  • A doc comment on a public API starts with a one-line summary. Add only what the signature cannot say, such as units, errors, side effects or threading.
  • Every TODO has a ticket number, for example TODO(CB-412).
  • No banners, ASCII boxes or decorative dividers.

Commit messages

  • The subject line is in the imperative mood, 72 characters at most, with no full stop. It should finish the sentence "If applied, this commit will...".
  • Use the repo's prefix convention if it has one, such as fix: or feat:.
  • Leave a blank line, then write the body. Wrap it at 72 characters.
  • The body says why. Include what a reviewer cannot see in the diff, such as the bug, its cause or a trade-off.
  • Skip the list of changed files. The diff already shows them.
  • No emoji, gitmoji or marketing words. Never start with "This commit".

## Writing style

Write in plain English.

* Start with the answer. No preamble and no closing summary.
* Short sentences of about 15 words. Everyday words.
* Keep every fact, name, number, path and identifier exact.
* Use full stops. No dashes between clauses. No asides in brackets.
* Cut filler words: robust, seamless, comprehensive, leverage, ensure.
* Code comments explain why. Never describe a change in a comment.
* Commit subjects are imperative, 72 characters at most, with no emoji.
* Describe code as it is. Never write "I've updated" or "this ensures".

Foundations here

F2
C90 and PL enforce the complexity, branch and argument limits. For a list of cases, use match or a dict lookup.
F3
F401 and F841 catch unused imports and variables. ERA001 catches commented-out code.
F4
Use @dataclass(frozen=True, slots=True) for values and validate in __post_init__. Use Pydantic models only at the edges.
F5
dict.setdefault, list.pop and generators are the allowed exceptions.
F8
A concrete subclass never raises NotImplementedError. Only an abc.ABC base may leave a method abstract.
F9
Use typing.Protocol, declared in the module that calls it. No inheritance is needed.
F10
Domain modules never import sqlalchemy, httpx or boto3. FastAPI Depends wires in the concrete class.

House rules

  • Type hints on every function. An Any in a signature needs a comment explaining it.
  • Never write a bare except:. Catch the narrowest exception. Re-raise with raise NewError(...) from err.
  • No blocking IO inside async def. Use an async driver or run_in_threadpool.
  • No mutable default arguments. Default to None and build the value inside.
  • SQL is always parameterised. Never build a query with f-strings or %.

F10

F5

House rules

  • Never block the event loop. No *Sync file or crypto calls while handling a request. Move CPU-heavy work to worker_threads or a queue.
  • Read environment variables once at startup. Validate them with a schema and exit on failure. Nothing else reads process.env.
  • One error handler maps domain errors to HTTP status codes. Stack traces never reach the client.
  • Log structured JSON. Never log tokens, passwords or personal data.
  • On SIGTERM, stop taking requests and finish in-flight work. Then close pools and exit.
  • SQL is always parameterised. Commit the lockfile and install with npm ci in CI.

Foundations here

F1
A component with a boolean prop per variant is really several components. Replace flags such as isDanger with explicit variants such as <Alert.Destructive>, or pass children.
F2
Stylelint caps nesting at 3 levels and bans ID selectors and !important. Split a component when its JSX runs past one screen.
F3
knip finds unused components. Keep a component's styles in its folder, so deleting the component deletes them too.
F4
A compound component keeps shared state in one context that the parent owns. Children read it. They never copy it into their own state.
F5
Render is a query. It never fetches, navigates or writes to the DOM. Event handlers and effects make changes.
F10
Components never call fetch. Data arrives through a hook or server loader that wraps the API client.

Accessibility

  • Use the element that does the job. <button> runs an action. <a href> goes somewhere. Never put a click handler on a <div>.
  • Every input has a visible <label>. Placeholder text is not a label.
  • Every focusable element shows a ring on :focus-visible. Never remove an outline without drawing a replacement.
  • Tab order follows the visual order. Never set a positive tabindex.
  • A skip link is the first focusable element on every page. It jumps to <main>.
  • Escape closes a modal. Focus then returns to the control that opened it.
  • An icon-only button has an aria-label that names its action.
  • Text contrast is at least 4.5:1. Large text, icons and input borders need 3:1. Check both themes.
  • Colour is never the only signal. An error shows text or an icon as well as a red border.
  • One <h1> per page. Headings go down one level at a time.
  • Link text makes sense on its own. Never write "click here" or "read more".
  • Every image has alt text that says what it shows. A decorative image gets alt="".

Look and feel

  • Colours, fonts, spacing, radii and shadows are CSS custom properties defined in one file. Stylelint blocks hex colours everywhere else.
  • Every token has a dark theme value. Check borders and translucent surfaces in both themes. A white card at 10% opacity vanishes on a light page.
  • Touch targets are at least 44 by 44 CSS pixels. WCAG 2.2 AA asks for 24. We use the stricter AAA size.
  • Pages work at 320 CSS pixels wide with no sideways scroll.
  • Every interaction shows feedback within 100 ms. Show a pressed state first. Add a spinner if the work takes longer.
  • Clickable elements set cursor: pointer.
  • Transitions last 150 to 300 ms. Animate only transform and opacity. Put motion inside @media (prefers-reduced-motion: no-preference).

Performance

  • Start independent requests together with Promise.all. Awaiting one before starting the next is a waterfall.
  • Import from the module that defines the thing, not from an index.ts barrel. Barrels can pull a whole library into the bundle.
  • Load heavy components on demand with React.lazy or next/dynamic, inside a <Suspense> boundary.
  • Give every image a width and height. The page then does not jump as images load.
  • Long lists use content-visibility: auto or a virtual list.

Cost and legal risk

Public web apps · hosting, data, consent, email, payments and uploads

A public web app can run up a large bill or a lawsuit before it has users. Everything in Web design applies. These rules close the holes that cost the most.

WarningThese are code fixes, not legal advice. The laws named here are American. UK and EU law differ and are often stricter. A lawyer reads the policy pages, consent text and email footers before launch.

Gatee2e/third-party.spec.ts
import { expect, test } from "@playwright/test";

The test fails on a remote font, a CDN script, an analytics tag or a session recorder that loads before the visitor consents.

Hosting and spend

  • Rate-limit every public endpoint per IP address. Put a limit on the site as a whole too.
  • Serve any static file over 200 KB from a CDN with cache headers, or from object storage.
  • Set a hard spend cap in config. A budget alert only tells you about the bill. If the host has no config setting for it, name the dashboard setting in the README.
  • Set concurrency and maximum instances explicitly. Platform defaults can reach 1000 instances.
  • A function never calls or queues itself without limits. Give recursion and fan-out a depth limit, a visited set and a maximum number of attempts.
  • Every outbound call has a timeout.
  • Remove third-party scripts that load with the page but do nothing you use.

Data and secrets

  • Every table has row level security turned on. Owners reach only their own rows. Everything else runs on the server with the service role.
  • Firebase projects put the same rules in firestore.rules or database.rules.json.
  • Service role keys, secrets and admin credentials stay on the server. Never put them in NEXT_PUBLIC_* or VITE_* variables or a committed .env file. Both prefixes ship to the browser.
  • Check the client bundle, git history and logs for secrets. Rotate any key you find. Deleting it from the latest commit is not enough.
  • An API route reads the user from the session. It never trusts a user id from the body or URL.
  • Sign-in and password reset give the same response whether or not the account exists. Otherwise anyone can test which emails have accounts.
  • Sign-out ends the session on the server. Clearing the browser's copy is not enough.

Privacy and consent

  • Self-host fonts with a local @font-face. Remove remote font <link> and @import lines. A remote font sends every visitor's IP address to the font host.
  • Bundle CSS and JavaScript too. Loading them from Typekit, jsDelivr, unpkg or cdnjs leaks the same data.
  • Keep a list of each third-party script that remains and the data it receives.
  • Load no analytics and set no tracking cookies until the visitor consents. Store the choice. Let them change it at any time.
  • Session replay is off by default. That covers PostHog, Hotjar, FullStory, LogRocket, Clarity, Mixpanel and Sentry Replay. Heatmaps, keystroke logging and rage-click recording count too. Recording without consent risks a CIPA claim.
  • Replay starts only after explicit opt-in. Mask every input. Never record password, payment or email fields.
  • Sign-up checks on the server that the visitor is 13 or older, before creating the account. Stop an under-13 attempt and store nothing from it. Newsletter, waitlist and contact forms run the same check. COPPA sets this rule.
  • The footer and the sign-up form link to the privacy policy and terms. The privacy policy names every processor the code sends data to.

Email and SMS

  • SMS needs prior express written consent. Ask with a checkbox that starts unchecked. Its text says what messages they get and how often. It says consent is not a condition of purchase, and that replying STOP unsubscribes.
  • Store each consent with a timestamp and the exact text shown.
  • Handle STOP and HELP replies.
  • Every commercial email has a one-click unsubscribe link and a physical postal address. It also sends the List-Unsubscribe and List-Unsubscribe-Post headers. CAN-SPAM sets these rules.
  • Mark transactional emails in code. Anything unmarked follows the commercial rules.
  • The send path checks the suppression list before every send. An unsubscribe then applies at once, well inside the 10 business days the law allows.
  • Rate-limit bulk sends and remove duplicate recipients.

Subscriptions

California's automatic renewal law sets these rules.

  • Next to the pay button, show the price and how often it renews. Say that it renews until cancelled, and how to cancel.
  • Take affirmative consent to those terms. A box ticked in advance does not count.
  • Cancelling works inside the app and is as easy as signing up.
  • A confirmation email repeats the terms and how to cancel.
  • A free trial sends a reminder email before the first charge.

User uploads

  • Publish a copyright policy page. It gives the DMCA takedown procedure, an email address for notices and a repeat infringer policy.
  • Put a "Report copyright infringement" link next to uploaded content.
  • Register a designated agent at copyright.gov/dmca-directory before launch. It costs $6. Renew it every three years.

Search engines

Public pages · titles, crawling, speed, snippets and structured data

Search engine optimisation, or SEO, decides whether people find a public page. Everything in Web design applies. These rules help a crawler read the page, keep it fast and let Google quote it in a featured snippet.

WarningSigned-in pages stay out of search. Titles, descriptions and snippets show up in results, browser history and shared links. Never put personal or health data in one.

It also fails when a signed-in page lacks noindex or a missing page returns 200. Lighthouse runs in a lab and cannot measure INP. Total Blocking Time stands in for it.

Titles and descriptions

  • Every public page has its own <title> of 60 characters or fewer. Put the main search phrase first and the brand last.
  • Every public page has its own meta description of 50 to 155 characters. Write it as the answer the page gives. Google shows it under the title unless it prefers text from the page.
  • The <h1> names the same topic as the title. The two need not match word for word.
  • Name image files for what they show, such as care-plan-review.webp. Serve AVIF or WebP at the size the image displays.
  • Google indexes the mobile version of a page. The mobile layout keeps the same text, headings, links and structured data as desktop.

Crawling and URLs

  • Put the text a page should rank for in the HTML the server sends. Render public pages on the server or at build time. Google runs JavaScript later, in a second pass. Many other crawlers never run it.
  • Flutter web draws the page on a canvas, so crawlers see no text. Build public pages in HTML. Keep Flutter web for the signed-in app.
  • Each page has one URL. Its <link rel="canonical"> gives that URL in full. Pick one host, one protocol and one trailing slash rule. Every other form redirects to it with a 301.
  • A moved page redirects with a single 301 to its final address. Never chain redirects. Update internal links to point at the final address.
  • A missing page returns status 404. A "not found" page served with 200 gets indexed as an empty page. Single-page apps do this by default.
  • Generate sitemap.xml from the route table. List only public pages that return 200 and are their own canonical. Give each a lastmod date. Name the sitemap in robots.txt.
  • Signed-in pages send X-Robots-Tag: noindex. So does every response from a staging or preview host.
  • Never block a signed-in path in robots.txt. A blocked crawler never sees the noindex, and Google can still list the URL from links.
  • Verify Google Search Console with a DNS record. The analytics method needs a tracker on the page, which the third-party check fails.

Speed

  • Google uses three Core Web Vitals as ranking signals. Largest Contentful Paint, or LCP, times the main content. Interaction to Next Paint, or INP, times the response to a tap or key. Cumulative Layout Shift, or CLS, scores how much the page jumps.
  • At the 75th percentile of real visits, LCP is 2.5 s or less, INP is 200 ms or less and CLS is 0.1 or less.
  • INP replaced First Input Delay in March 2024. Ignore advice that still targets FID.
  • The Lighthouse score is not a ranking signal. Fix a PageSpeed warning for rank only when it moves one of the three vitals.
  • Never lazy-load the largest image above the fold. Give it fetchpriority="high". If the largest element is text, preload its font.
  • Reserve space for anything that loads late, such as embeds, images and banners. Pin a consent banner to the viewport so it covers content instead of pushing it down.
  • Check the field numbers in Search Console each month. The lab numbers from the gate only predict them.

Site structure and links

  • Group pages by topic. Each topic has one pillar page that covers it broadly. Each supporting page answers one question in depth and links to the pillar. The pillar links to every supporting page.
  • Each page targets one search phrase and one intent. Two pages that target the same phrase compete, and both rank lower. Merge them and redirect the weaker one with a 301.
  • Every public page has at least one link from another page. A page reached only through the sitemap is an orphan. It gets no ranking weight from the rest of the site.
  • Internal links are plain <a href> elements. Crawlers do not click buttons or run router calls.
  • Link text names the topic of the page it opens. The accessibility rules already ban "click here".
  • Public URLs are short lowercase words joined by hyphens, such as /guides/care-plan-review. Leave ids and tracking parameters out of them.

Featured snippets

A featured snippet is the answer box above the first result. Google fills it from a paragraph, list or table on a page that already ranks in the top ten.

  • Phrase a heading as the question people search. Questions that start with who, what, where, when, why or how win snippets most often. So do step-by-step searches.
  • Answer the question in the first paragraph under the heading, in 40 to 60 words. Start with the answer, then explain it.
  • Put steps in an <ol>, one step per item, each starting with a verb. Put comparisons in a <table> with a header row. Google lifts lists and tables straight into the snippet.
  • A short FAQ section of real questions can win snippets and People Also Ask boxes. Give each question its own heading.
  • Since August 2023, Google shows FAQ rich results only for well-known government and health sites. It shows no HowTo rich results at all. Skip HowTo markup. Add FAQPage markup only if the site qualifies.

Structured data

  • Describe each public page in JSON-LD, inside a <script type="application/ld+json">. Use Organization on the home page, Article on guides and posts, SoftwareApplication on product pages and BreadcrumbList on anything nested.
  • Build the JSON-LD from the same data the page renders. Hand-written markup drifts from the page. See F1.
  • Mark up only what a visitor can see on the page. Google can remove rich results from a site whose markup hides or misstates content.
  • Escape < in JSON-LD as <. Otherwise page text can close the script tag.
  • Run each new page type through Google's Rich Results Test before merge. The gate only checks that the JSON parses.

The first page gives every guide the title "Guides", with no description or canonical link. A crawler sees no heading and no list, so there is nothing to lift into a snippet. The second builds the metadata and JSON-LD from one guide, so they cannot drift. The title is the question and guide.answer is the 40 to 60 word reply. metadataBase in the root layout turns the canonical path into a full URL. articleJsonLd escapes <.

Using an assistant

An assistant drafts search copy quickly. It cannot see real search data. Check every number it gives before you plan work on it.

  • Ask for five titles and five descriptions from different angles, inside the length limits. Pick one of each and edit it to the Writing rules.
  • Paste a crawl report or PageSpeed result and ask for the issues ranked by effect on rank. Check that order against the rules above.
  • Search volume and difficulty from an assistant are guesses. Confirm them in Search Console or a keyword tool.
  • Never paste customer records or analytics exports with personal data into a prompt.
Promptbrief for a new public page
Act as an SEO editor. I am writing a public page for [audience].
The main search phrase is [phrase]. The intent is [informational or commercial].
Our current pages and their main phrases are: [list].

Give me:
1. Five titles of 60 characters or fewer, each from a different angle.
2. Five meta descriptions of 50 to 155 characters.
3. An outline of H2 and H3 headings. Phrase each H2 as a question people search.
4. A 40 to 60 word answer to the question most likely to win a featured snippet.
5. Which sections suit a numbered list or a table.
6. The schema.org type for the page, and why.
7. Which current pages should link to this one.

Flag any current page that already targets this phrase.

Item 7 and the last line catch an orphan page, or two pages competing for one phrase, before the page exists.

These skills take the repetitive work, such as contrast checks, responsive variants and audits against checklists. The designer still makes the decisions. A skill's review is advice. Before you install a skill

  • Read SKILL.md in full. A skill runs with your permissions. A malicious one can hide a reverse shell in its instructions.
  • Check the allowed-tools field in its frontmatter. A design skill that asks for shell or network access needs a reason you can name.
  • Read every bundled script line by line, Python especially. UI/UX Pro Max runs a Python search script. Its README says the script uses only the standard library and makes no network calls. Confirm that in the code.
  • Update a skill by pull request, like any other dependency. Record the source commit each time.
